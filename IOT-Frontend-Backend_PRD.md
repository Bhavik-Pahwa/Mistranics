# INDUX — Hardware-to-Frontend Integration PRD

**Sprint:** Evaluation Round — Hardware & Live Telemetry  
**Priority:** Critical  
**Status:** Implementation specification  
**Scope:** One temperature sensor, two selectable data sources, MQTT ingestion, in-memory anomaly detection, live frontend visualization.

---

## 1. Objective

Implement a working end-to-end telemetry pipeline for INDUX.

The application must allow the evaluator to choose between:

1. **Physical Sensor Mode:** Temperature readings from the DS18B20 probe connected to the ESP32.
2. **Simulation Mode:** Temperature readings generated by the existing online motor simulation.

Regardless of the selected source, readings must follow the same backend processing pipeline:

**Data Source → MQTT Broker → Backend Subscriber → Validation → 3-Second Window Processing → Statistical Anomaly Detection → Frontend**

The frontend must display incoming temperature readings in near real time and visibly identify anomalous readings.

### Sprint success criteria

- Physical DS18B20 readings reach the backend through MQTT.
- Simulated readings can enter the same MQTT pipeline.
- The frontend can switch between physical and simulated sources.
- Temperature readings are plotted live.
- Anomalies are detected and visibly marked.
- The complete flow works without a database or ML model.

## 4. Data source architecture

### 4.1 Physical sensor mode

Hardware flow:

**DS18B20 → ESP32 → Wi-Fi → MQTT Broker → Backend**

The ESP32 must:

- Read temperature from the DS18B20 probe.
- Sample the sensor at approximately one-second intervals, subject to successful sensor conversion.
- Aggregate valid readings into three-second windows.
- Calculate the window features.
- Publish one telemetry message per completed window.
- Include timestamps, device identity, sequence number and sensor status.
- Publish using the common telemetry schema.

The DS18B20 is a relatively slow temperature sensor. Do not treat it like a high-frequency vibration sensor.

For this sprint, the following features are sufficient:

| Feature            | Description                        |
| ------------------ | ---------------------------------- |
| `temperature_mean` | Mean temperature during the window |
| `temperature_min`  | Minimum valid temperature          |
| `temperature_max`  | Maximum valid temperature          |
| `sample_count`     | Number of valid samples            |
| `sensor_status`    | Valid, missing or error            |

If only one valid sample is available, the mean, minimum and maximum may all equal that sample. Do not manufacture additional samples.

### 4.2 Simulation mode

The existing motor simulation must be adapted to publish through the same MQTT ingestion path.

**Simulation → MQTT Publisher/Adapter → MQTT Broker → Backend**

Requirements:

- Reuse the existing simulation logic.
- Do not duplicate the simulation unnecessarily.
- Extract its temperature readings.
- Aggregate readings into three-second windows.
- Publish the same schema used by the ESP32.
- Include `source: "simulation"` in the message.
- Preserve the simulation's existing ability to represent different motor operating conditions.

If the simulation currently runs entirely in the browser, implement a small adapter that forwards its generated readings to MQTT. Do not bypass MQTT and send simulation readings directly to the frontend.

The simulation must not pretend to be a physical sensor.

### 4.3 Source selection

Add a source selector to the frontend:

- Physical Sensor
- Simulation

The selected source determines which telemetry stream the backend processes and forwards to the dashboard.

Recommended behavior:

1. Frontend sends the selected source to the backend.
2. Backend updates its active source.
3. Backend accepts and processes readings from that source.
4. Readings from the inactive source are ignored for dashboard updates and anomaly calculations.
5. Frontend displays the active source clearly.

Use a small backend endpoint, for example:

`POST /api/source`

Example request:

```json
{
	"source": "physical"
}
```

Allowed values:

- `physical`
- `simulation`

Return the currently active source in the response.

**Important:** Source selection is not a claim that the other publisher has stopped. It only controls which stream the application uses. If practical, pause the simulator publisher when physical mode is selected.

## 5. MQTT integration

Use the existing MQTT broker if one is already configured. Otherwise, use Eclipse Mosquitto for local development.

### Suggested topics

```text
indux/device-01/telemetry
indux/device-01/status
```

Both physical and simulated sources should publish to the telemetry topic using the same schema.

The `source` field distinguishes the publisher.

### Common telemetry schema

Example physical sensor message:

```json
{
	"schema_version": 1,
	"device_id": "device-01",
	"source": "physical",
	"sequence": 12,
	"window_start": "2026-11-03T00:00:00Z",
	"window_end": "2026-11-03T00:00:03Z",
	"window_duration_seconds": 3,
	"temperature": {
		"mean": 32.4,
		"min": 32.3,
		"max": 32.5,
		"unit": "degC",
		"sample_count": 3,
		"status": "valid"
	}
}
```

Example simulation message:

```json
{
	"schema_version": 1,
	"device_id": "simulation-01",
	"source": "simulation",
	"sequence": 12,
	"window_start": "2026-11-03T00:00:00Z",
	"window_end": "2026-11-03T00:00:03Z",
	"window_duration_seconds": 3,
	"temperature": {
		"mean": 48.2,
		"min": 47.9,
		"max": 48.6,
		"unit": "degC",
		"sample_count": 3,
		"status": "valid"
	}
}
```

These are illustrative payloads, not actual sensor readings.

### MQTT requirements

- Use JSON payloads.
- Use QoS 1 for telemetry initially.
- Include a monotonically increasing sequence number per publisher.
- Validate incoming payloads before processing.
- Handle malformed JSON and missing fields without crashing.
- Handle MQTT disconnection and reconnection.
- Do not assume QoS 1 guarantees exactly-once processing. Use sequence numbers to identify duplicates.
- Do not use `localhost` as the broker address in ESP32 firmware. Use the laptop's LAN IP address.

## 6. Backend implementation

The backend must become the central ingestion and processing point.

### 6.1 MQTT subscriber

Implement or adapt a subscriber that:

1. Connects to the MQTT broker.
2. Subscribes to the telemetry topic.
3. Receives incoming messages.
4. Decodes JSON.
5. Validates the schema.
6. Checks the active source.
7. Rejects duplicate or invalid messages where applicable.
8. Sends valid messages to the processing pipeline.

The MQTT subscriber must run alongside the existing backend application, not block its HTTP server.

Use the project's existing asynchronous or background-task approach where practical. Avoid introducing a complex message-processing framework.

### 6.2 Validation

Validate:

- `schema_version`
- `device_id`
- `source`
- `sequence`
- `window_start`
- `window_end`
- `temperature.mean`
- `temperature.min`
- `temperature.max`
- `temperature.unit`
- `temperature.sample_count`
- `temperature.status`

Reject invalid numeric values, including NaN and infinity.

If the sensor reports an error or missing reading, update the connection/sensor status but do not run anomaly detection on invalid data.

### 6.3 Three-second processing windows

The ESP32 and simulation adapter are responsible for producing three-second feature summaries.

The backend should consume these summaries rather than attempting to reconstruct raw sensor windows.

For this sprint:

- One completed feature window should produce one processing event.
- Do not wait for multiple MQTT messages to create another three-second window.
- Do not accidentally aggregate three-second summaries into another three-second window.
- Preserve the original window timestamps.
- Keep the processing pipeline independent of the source.

### 6.4 In-memory state

No database is required.

Maintain:

- Latest valid temperature reading.
- Latest processed window.
- Recent temperature history for charting.
- Recent baseline values for anomaly detection.
- Current anomaly status.
- Active data source.
- Last message timestamp.
- MQTT and sensor connection status.

Use bounded in-memory collections, such as a deque or fixed-size list.

A restart may clear this state. That is acceptable for this evaluation sprint.

## 7. Anomaly detection

### 7.1 Decision

For this sprint, bypass Isolation Forest in the decision layer.

Use a lightweight statistical detector on the incoming temperature window summaries.

Do not delete the existing Isolation Forest implementation. Keep it inactive and avoid spending time refactoring it.

### 7.2 Statistical approach

Use the `temperature.mean` value of each valid three-second window.

Maintain a rolling baseline using previous valid windows.

Recommended initial implementation:

- Baseline history: last 20 valid windows.
- Minimum baseline samples: 5.
- Anomaly threshold: absolute Z-score greater than or equal to 3.
- Calculate the baseline using previous windows, excluding the current reading.
- Update the baseline only after the current reading has been evaluated.
- Use a small standard-deviation floor to avoid division by zero.
- If insufficient baseline samples exist, return `WARMING_UP`.

Formula:

\[
z = \frac{x-\mu}{\max(\sigma,\epsilon)}
\]

Where:

- \(x\): current window mean.
- \(\mu\): mean of the baseline.
- \(\sigma\): baseline standard deviation.
- \(\epsilon\): small configurable minimum standard deviation.

Decision:

```text
IF sensor_status != valid:
    status = SENSOR_ERROR

ELSE IF baseline_samples < minimum_samples:
    status = WARMING_UP

ELSE:
    calculate z_score

    IF abs(z_score) >= threshold:
        status = ANOMALY
    ELSE:
        status = NORMAL
```

Return:

```json
{
	"status": "ANOMALY",
	"method": "STATISTICAL_Z_SCORE",
	"value": 48.2,
	"baseline_mean": 32.4,
	"baseline_std": 1.1,
	"z_score": 14.36
}
```

The values above are illustrative.

### 7.3 Important limitations

A statistical deviation is not proof of a mechanical fault.

A high temperature reading may reflect a different operating speed, ambient conditions, or load rather than a defect.

Therefore:

- Label the output **Statistical Anomaly**, not confirmed motor failure.
- Do not claim the system has diagnosed a particular fault.
- Do not invent manufacturer-approved motor temperature limits.
- Make the Z-score threshold and baseline size configurable.
- Do not silently classify readings as normal during baseline warm-up.

If the simulation includes known operating conditions, use them to demonstrate different data patterns, but do not use the simulation's hidden condition labels as the detector's answer.

### 7.4 Optional absolute threshold

If a verified motor-specific temperature limit becomes available, an additional absolute-limit check can be added.

For now, do not hardcode an arbitrary temperature and call it a manufacturer limit.

## 8. Backend-to-frontend communication

The frontend must receive processed readings without polling the database.

Use the existing real-time communication mechanism if available.

Otherwise, implement a WebSocket endpoint, for example:

```text
/ws/telemetry
```

For each processed window, send a message containing:

```json
{
	"source": "physical",
	"timestamp": "2026-11-03T00:00:03Z",
	"temperature": 32.4,
	"unit": "degC",
	"anomaly": {
		"status": "NORMAL",
		"method": "STATISTICAL_Z_SCORE",
		"z_score": 0.42
	},
	"sensor_status": "valid"
}
```

The backend must broadcast only readings from the currently selected source.

Handle WebSocket disconnections and reconnects without crashing the backend.

A REST endpoint may also be provided to fetch the latest reading and current source when the dashboard first loads.

Suggested endpoints:

| Endpoint                    | Purpose                        |
| --------------------------- | ------------------------------ |
| `POST /api/source`          | Change active data source      |
| `GET /api/source`           | Get active data source         |
| `GET /api/telemetry/latest` | Fetch latest processed reading |
| `GET /api/status`           | Get MQTT and sensor status     |
| `WS /ws/telemetry`          | Stream processed readings      |

Reuse existing endpoints if equivalent functionality already exists.

## 9. Frontend implementation

Modify the existing dashboard rather than creating a new page.

### 9.1 Source selector

Add a visible selector:

- Physical Sensor
- Simulation

Display the currently selected source in the dashboard.

When the source changes:

1. Send the source selection to the backend.
2. Wait for confirmation.
3. Clear or separate the previous source's chart history.
4. Display readings from the newly selected source.
5. Update the connection status.

Do not show stale physical readings as if they came from the simulator, or vice versa.

### 9.2 Live temperature chart

Create or adapt a live temperature chart.

Requirements:

- X-axis: timestamp.
- Y-axis: temperature in °C.
- Append new readings as they arrive.
- Keep a bounded number of recent points, such as 60.
- Do not reload the whole page for each update.
- Visually distinguish anomalous points from normal points.
- Preserve the selected source context.

The chart must display actual values received from the backend, not hardcoded demo data.

### 9.3 Current reading

Display:

- Latest temperature.
- Unit (°C).
- Selected data source.
- Last update time.
- Sensor/stream connection state.

### 9.4 Anomaly indicator

Show a clear status:

- `NORMAL`
- `ANOMALY`
- `WARMING UP`
- `SENSOR ERROR`
- `DISCONNECTED`

When an anomaly occurs, display:

- Current temperature.
- Z-score.
- Baseline mean.
- Detection method.
- Timestamp.

Do not display an anomaly alert for invalid or missing sensor data.

### 9.5 Connection status

Display the status of:

- MQTT connection as known by the backend.
- Physical sensor stream, when physical mode is selected.
- Simulation stream, when simulation mode is selected.
- Frontend WebSocket connection.

A lack of new data should eventually be shown as stale or disconnected. Do not leave an old reading displayed with a misleading live indicator.

## Final implementation principle

**Make the complete data path work before improving anything else.**

The priority is not sophisticated AI. The priority is proving that INDUX can acquire a real temperature measurement, transport it through MQTT, process it in the backend, identify a statistical deviation, and display the result on the dashboard.

Do not fake the physical data, bypass MQTT for the simulation, hardcode chart values, or claim a statistical anomaly is a confirmed mechanical fault.

Build the smallest reliable implementation that demonstrates the entire pipeline.
